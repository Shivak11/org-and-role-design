# Workbook record, version 1

New interviews start with [recording-guide.md](recording-guide.md) and `scripts/session.py`. This is the detailed field reference. Structural validation permits incomplete drafts; the new session path separately checks final-stage completeness.

The host agent writes JSON from confirmed conversational answers. The participant never fills this structure. All textual fields are plain text; escape them when producing HTML. Empty lists and explicit unknown text are acceptable in a draft. Do not manufacture values to complete a diagram.

Top-level fields:

- `schema_version`: 1.
- `title`: plain title naming the function.
- `status`: `draft` or `confirmed`. `confirmed` means the participant accepted this design as an exercise record, never production authorisation.
- `confirmation`: `{accepted: boolean, revision: integer, wording: string}`. Accepted requires a nonempty actual participant confirmation, and revision equal to the top-level revision. Draft uses false.
- `revision`: positive integer.
- `organisation`: `{label, scope, horizon, context, exclusions}`; all strings. An anonymised label is sufficient.
- `evidence_note`: string explaining the basis and gaps.
- `outcomes`: list of `{id, name, owner_id, success, basis}`. owner_id refers to proposed_roles.
- `current_roles` and `proposed_roles`: lists of `{id, label, parent_id, scope, responsibilities: [string], change, reason}`. `parent_id` is null or an ID in the same list. Role IDs can recur across the two lists; IDs are unique within each list. Arbitrarily deep valid trees, multiple roots, and explicit external shared-service roles are supported. Do not infer headcount from role nodes. `change`: retained / changed / proposed / unknown. `reason` records the rationale, or says no reporting change proposed.
- `services`: list of `{id, label, outcome_owner_id, supervisor_id, service_owner_id, availability, shared_with, agent_roles}`. All non-null owner IDs refer to proposed human roles. `availability`, `shared_with` are strings. `service_owner_id` may be null in a draft or conditional proposal; display "Service owner to confirm" visibly. `agent_roles`: list of `{id, label, tasks: [string], autonomy, inputs, outputs, tools: [string], escalation_to_id, escalation_condition, instances}`. `instances` is null when unknown/variable or a positive integer provided by the participant; label as running instances, never as staff. `autonomy`, `inputs`, `outputs` are strings. An agent role has a unique ID across all services. Escalation refers to a proposed human role. No cross-agent ownership counts as human accountability.
- `workflows`: list of `{id, label, outcome_id, coverage, current, proposed}`. Coverage states whether traced in detail or only described at a high level. Each current/proposed step: `{id, action, actor_type, actor_id, actor_label, owner_id, input, output, approval_by_id, condition}`. `actor_type`: human / agent / software / external. Human actor IDs refer to the relevant current/proposed role list. Proposed agent IDs refer to agent_roles. A current agent step uses null actor_id and a nonempty actor_label describing the existing agent; its owner is a current human role. Do not misclassify existing agents as software or new proposals. Software/external use null actor_id and a descriptive actor_label. `owner_id`, when supplied, refers to a human role in the relevant side. `approval_by_id` is null or a human ID in that side. The actor does the work; owner remains accountable. Preserve sequence; do not force one-to-one step alignment. Each step has a visible input and returned output. `condition` can explain the trigger, stopping rule, handoff or exception. Current and proposed step IDs unique within their sequence.
- `work_changes`: list of `{current_work, change, future_work, executor, owner_id, capability, basis}`. owner_id refers to proposed human role. Show what stops, changes, continues, appears or moves; do not translate hours saved into jobs cut.
- `levers`: list of `{name, current, proposed, reason, basis}`. Include only conclusions supported by the record, and explicitly identify any dimensions not yet assessed. Common dimensions: hierarchy, centralisation, span of human supervision, agent oversight, decision rights, specialisation, departmentalisation, formalisation, standardisation, coordination, capacity, external dependence, measures.
- `readiness`: list of `{need, status, owner_id, validation}`. owner_id nullable; status plain text distinguishing available, assumed, to verify, and unavailable. Covers prompt instructions, skills/procedures, data/context, connectors including MCP/API, ordinary software, checks, permissions, and case records as needed. Do not fill every category automatically.
- `pilot`: `{scope, owner_id, measure, baseline, success, stop, review_date}`; strings except owner_id. owner_id may be null in a draft and must identify a proposed human role for a confirmed record. Unknown baseline is a string saying not measured. Values must come from participant or be visibly proposed in the wording.
- `open_questions`: list of strings.
- `history`: list of `{revision, initial_choice, ai_proposal, participant_decision, note}`. Preserve an actual prior choice or say not provided; never invent it.

Renderer command, run from the participant's working directory with `$SKILL` set to this skill folder: `python3 "$SKILL/scripts/render_workbook.py" session.json workbook.html`. CLI should accept positional input and output, plus `--validate-only`. Renderer validates before writing. All HTML/CSS must be self-contained, with a print action, no network dependencies and no data posted anywhere. An example outside the distributable skill will supply realistic records.

Draft uncertainty: outcomes.owner_id, service outcome_owner_id/supervisor_id, agent escalation_to_id, workflow owner_id and work_changes owner_id may be null in a draft. Render the exact unresolved responsibility as "to confirm". Do not invent a person or deploy a workflow with unresolved ownership. A confirmed record requires these essential human references. Non-null references must always resolve to the correct human role set.

Validation requirements: check structure, field types, duplicate IDs, role reporting cycles, dangling owners/actors, invalid instance counts (reject bool), wrong-side role references, missing human supervisors and outcome owners in confirmed records, confirmation mismatch. A service owner may remain unknown and an input can be explicitly uncertain. Reject markup injection only by escaping, not by deleting participant wording. Do not infer real-world feasibility from successful validation.

Visual requirements: use the bundled editorial style and Sketchyicons defined in [the comparison record](comparison-record.md) and [the visual style](visual-style.md) for new charts. Human circles, agent clipped-corner shapes and paired icons distinguish execution; labels identify human-only, agent-only, human-plus-agent, ordinary software and unknown. Agent groups do not establish counts. Pair current and proposed division, reporting and decision authority. Keep unknown earlier practice visible and do not infer a change from a newly specified responsibility. Use dynamic content height and readable expansion for large scopes. Current/proposed trees are side by side on wide screens and individually readable on narrow screens. Preserve full text, a line key, scope, basis and author attribution. No italics or decorative label layers.

The version 1 fields above remain supported. For the default current/proposed diagram renderer, add the `comparison` extension described in [comparison-record.md](comparison-record.md). Optional role `node_type`, `size` and `reporting_status` distinguish named people, role patterns, aggregated units, known parents and unknown relationships. A unit node cannot substitute for a named accountable human. Use `python3 "$SKILL/scripts/render_comparison.py" session.json comparison.html`; the detailed `render_workbook.py` output remains available as a supporting record. Do not use the older release-specific prototypes as the general-manager default.

The additive decision-level workflow contract is documented in the same comparison reference. Both renderers validate it. It adds unresolved actors, one-of eligible human performers, knowledge, bounded decisions, override and stop rights, escalation, handoff cost and typed links. A nonempty workflow list also appears in the comparison's Workflow view. The workbook preserves every field in the detailed record. No extension field is required for an older draft, and no missing step is inferred.
