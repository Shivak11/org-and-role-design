# Worked example: a shop's refund workflow

This is a fictional run. It shows the shape of each stage; never reuse its facts in a learner's record.

## The learner's answers

After choosing option 1, the learner wrote: "A customer gives the receipt to a sales associate. The associate checks the purchase record and messages the store manager. The manager decides. Accounts pays the refund. All refunds need manager approval, and six associates report to the manager. I want customers to wait less."

For the first change, the learner wrote: "I would let the associate decide refunds below Rs 2,000 after checking the receipt and purchase record, so that customers wait less. The manager handles everything else. Accounts still pays. We would write this rule down."

At the confirmation step, the learner replied: "Accept. This may run into difficulty when people split one large refund into several small ones; I would check it by observing repeated receipts from the same customer."

## The closing read-back

**What happened before**

1. The customer gives the receipt to a sales associate.
2. The associate checks the purchase record and messages the store manager.
3. The store manager decides every refund.
4. Accounts pays the refund.

**Your completed redesign**

1. The customer gives the receipt to a sales associate.
2. The associate checks the receipt and the purchase record.
3. For a refund below Rs 2,000, the associate decides. For any other refund, the associate messages the store manager, who decides.
4. Accounts pays the refund.

**What this changes in the organisation**

The decision on ordinary refunds moves from the store manager to the associate, which is bounded decentralisation: the manager keeps authority over larger refunds and exceptions. The Rs 2,000 limit is a common rule that every associate applies in the same way, so it standardises the decision, and writing it down formalises it. The store manager still has six direct reports, so the span of control is unchanged. The manager will approve fewer refunds, which may free time, but that is a hypothesis to test and does not change the span.

**What remains to check**

You expect customers to wait less; this has not been measured. You named one risk, split refunds, and one check, watching for repeated receipts from the same customer.

**How you used AI**

You supplied the workflow, the change and the limit. The AI kept the record and asked about the gaps. The habit to keep is to pick one part of a process that everyone treats as fixed, here "the manager approves every refund", and ask whether it needs to stay that way before asking AI to implement anything.

**Record for the next exercise**

- Workflow and intended result: shop refund; customers wait less.
- Before: associate checks, manager decides every refund, accounts pays.
- After: associate decides refunds below Rs 2,000 after checking the receipt and purchase record; manager decides the rest; accounts pays.
- Information and sources: receipt from the customer; purchase record from the shop system.
- Decision owners and limits: associate below Rs 2,000; store manager above it and for exceptions.
- Common rule and exceptions: written Rs 2,000 limit; larger refunds go to the manager.
- Direct reports: six before and after; reporting unchanged.
- Uncertainty and check: split refunds; watch for repeated receipts from one customer. Confirmed by the learner.

No agent role or automation has been chosen here. The workflow exercise is complete.
